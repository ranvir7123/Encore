Failed-debit recovery agent · UPI AutoPay & eNACH

Every retry has to get past a wall that cannot be argued with.

Encore decides when to retry a failed subscription debit. It never decides whether one is allowed. That belongs to a pure function with no network, no clock and no model behind it — and below, it is running in your browser on the same wall.py the test suite exercises. The agent that detects the failure, nudges, reads the reply and collects on a real Payment Link is in the repository; its one real rupee trail is below.

Read this before you quote a number

We ran the control that could kill our own headline. It killed the model. What ships has no model in it.

The interesting claim was that a trained model learned when customers have money. So we built random_in_horizon: a policy that picks its retry hour uniformly at random from the identical candidate set the model ranks, starting from the identical cooldown-aware hour. The only difference between them is whether the ranking is a model or a coin.

On held-out data the coin wins by {{RANDOM_MARGIN}}. It is not brute force — it recovered more using fewer attempts. A heuristic with no model at all (fixed_spread10: retry at T+3, T+6, T+9) gets most of the way there too. So the policy the agent ships, promise_aware_random, is the coin plus the customer's own reply: if they named a payday, retry on it; otherwise a uniform draw inside the compliant window. On this regime it beats the control by {{SHIPPED_OVER_RANDOM}}, read against a 2–3% noise floor between two random streams.

  • Holds The shipped policy beats the industry-standard T+1/T+2/T+3 schedule {{SHIPPED_RATIO}}, with {{VIOLATIONS}} compliance violations across all {{CELLS}} cells. Nothing in it is learned.
  • Does not hold That the model learned when customers have money. It reached {{LEARNED_RATIO}} over the industry schedule, and on the held-out regime a uniform draw over the same hours beats it by {{RANDOM_MARGIN}}.

Our first explanation was wrong too. We blamed a hardcoded near-payday flag in the feature vector, removed it, and retrained. The de-biased model gained 3% and still lost. The real cause is below, and it is a measurement problem rather than a modelling one. The model stays in the matrix as encore_learned so the comparison can be re-run; it is not in the agent.

Method · regime r1_shifted, held out from training · the model that did not ship

The model is not ignoring payday. It is two days early.

In this regime success is not a gradient — it is a step. Before day 25 a retry recovers almost nothing; from day 25 it recovers essentially everything, because salary has landed and the balance clears. Both policies face the same step. All that matters is how many of a capped three retries per customer land on the far side.

The model puts {{LEARNED_BEFORE}} retries on days 21–24, immediately before the cliff, and only {{LEARNED_AFTER}} past it. The uniform control lands {{RANDOM_AFTER}} past it. That gap is the whole result. A confident near-miss spends a capped budget on days that are reliably empty; a uniform draw at least samples the far side.
